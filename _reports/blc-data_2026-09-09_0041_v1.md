# BLC data: unflagged internal accounts polluting real-user metrics
Date: 2026-09-09 00:41 · Source: live `bloody` DB via /mcpb (Airbyte CDC replica)
Trigger: investigation of client 6052 ("why is the balance / sell-all so large?")

## Headline
**275 accounts that received manual admin balance adjustments are NOT flagged as
test accounts** (`is_real = true`, `flags = 0`) and therefore count as real users in
every standard query. Client 6052 is the worst single case.

## How the app is supposed to exclude test accounts
`public.clients` carries `is_real boolean` and a `flags` integer bitmask. The app's
own partial index defines the countable-user predicate:

    CREATE INDEX idx_clients_created ON public.clients (created)
      WHERE ((flags & 1) = 0 AND (flags & 64) = 0 AND deleted_at IS NULL);

So `flags & 64` is the "do not count" bit. There are also
`idx_clients_is_real` / `idx_clients_not_real` partial indexes on `is_real`.

## The leak
1,557 accounts have at least one `balances.reference_type = 4` row (manual admin
balance adjustment, bidirectional):

| bucket | accounts | admin credits |
|---|---|---|
| `flags & 64` set — correctly excluded | 1,259 | $2,576,573 |
| **Unflagged (`is_real=true`, `flags=0`)** | **275** | **$22,503** |
| Other flags (1, 8, ...) | 22 | $7,219 |
| `is_real=false` only | 1 | $225 |

### Two patterns — do not treat alike
- **Many small repeated grants** (6052: 316 x <=$20 over 2.5y) → test/QA behaviour.
- **One large grant 1-2 days after registration** (558750, 734997, 541107, 574775,
  522250: single $716-$876 credit) → looks like support compensation / promo payout,
  possibly real users. VERIFY before excluding.

## Case study: client 6052
- `is_real = true`, `flags = 0`, `partner_id = 1`, USD, kyc_approved = false,
  registered 2021-09-03, last login 2026-09-04.
- Real paid deposits: **$66.88** lifetime (20 deposits since 2021-09-22).
- Admin grants: **$6,275.20** across 316 credits, `info` values literally
  `test`, `cd test`, `t`, `qa`, `CB`, `cb` (309 with blank info).
  By year: 2023 = 16 / $305 · 2024 = 167 / $3,290 · 2025 = 136 / $2,680.20.
- Current cash balance: **$1.01**.
- Lifetime inventory: 25,930 items; 767 currently held ($2,295.47 buyout);
  551 sellable → **$2,116.70** (matches the site's "Sell all skins" figure exactly).
- 76 items ever worth >$100 ($36,723 total), **all already disposed**; zero held.
  None came from a plain paid case open — all from battles, free NFT drops,
  daily free cases, events and tournaments.

## Impact
Any deposit-conversion, GMV, ARPU, retention or drop-rate metric computed without
`(flags & 64) = 0` still includes these 275 accounts. 6052 alone contributes
$83.5k of recycled sell-back turnover on $66.88 of real deposits — it will badly
distort deposit-to-value ratios and case-drop EV analyses.

## Recommendation
1. Flag the confirmed internal accounts (`flags | 64`), starting with the low-ID
   cluster and 6052 — this is a dev-team change; we write the spec, they apply it.
2. Until then, every analysis query adds:
   `AND (c.flags & 64) = 0 AND c.id NOT IN (<unflagged internal list>)`.
3. Audit the "single large grant after registration" group separately — those may
   be legitimate compensation, not test accounts.

## SQL used
```sql
-- 1. exclusion-bucket sweep
WITH t AS (
  SELECT client_id,
         count(*) FILTER (WHERE amount > 0) AS credit_n,
         sum(amount) FILTER (WHERE amount > 0) AS credits_cents,
         sum(amount) FILTER (WHERE amount < 0) AS debits_cents,
         sum(amount) AS net_cents
  FROM public.balances
  WHERE _ab_cdc_deleted_at IS NULL AND reference_type = 4
  GROUP BY client_id
)
SELECT CASE
         WHEN c.id IS NULL THEN 'no client row'
         WHEN (c.flags & 64) <> 0 THEN 'flagged 64 (app-excluded)'
         WHEN coalesce(c.is_real,false) = false THEN 'is_real=false only'
         WHEN c.flags <> 0 THEN 'other flags'
         ELSE 'UNFLAGGED (counts as real)'
       END AS bucket,
       count(*), sum(t.credits_cents), sum(t.debits_cents), sum(t.net_cents)
FROM t LEFT JOIN public.clients c
  ON c.id = t.client_id AND c._ab_cdc_deleted_at IS NULL
GROUP BY 1 ORDER BY 3 DESC NULLS LAST;

-- 2. the unflagged exclusion list
WITH t AS (
  SELECT client_id, count(*) FILTER (WHERE amount > 0) AS credit_n,
         sum(amount) FILTER (WHERE amount > 0) AS credits_cents, max(created) AS last_at
  FROM public.balances
  WHERE _ab_cdc_deleted_at IS NULL AND reference_type = 4
  GROUP BY client_id
)
SELECT t.client_id, t.credit_n, t.credits_cents, t.last_at, c.created
FROM t JOIN public.clients c
  ON c.id = t.client_id AND c._ab_cdc_deleted_at IS NULL
WHERE (c.flags & 64) = 0 AND c.flags = 0 AND coalesce(c.is_real,false) = true
  AND t.credits_cents > 0
ORDER BY t.credits_cents DESC LIMIT 25;

-- 3. "Sell all skins" reproduction for 6052
SELECT count(*), sum(buyout_price)
FROM public.client_items
WHERE client_id = 6052 AND _ab_cdc_deleted_at IS NULL
  AND sold_at IS NULL AND status = 1 AND is_virtual_nft_item = false;
-- 551 | 211670  ==  $2,116.70
```

## Caveats
- `reference_type` has no documented enum. Type 4 = manual admin adjustment is
  inferred from `info` strings (`test`, `qa`, `cd test`) and is bidirectional
  ($2.58M credited vs $4.01M debited network-wide).
- `client_items.status` enum is inferred from data: `sold_at` is populated on
  statuses 4 and 11 (disposed); 1/8/9 are held; only status 1 non-NFT is sellable.
- `public.balances` has only a PK index — no index on `client_id` or `created`,
  so these are full table scans. Do not fan out per-account.
- CDC replica: matches the live site only as of last sync. The exact-cent match on
  "Sell all skins" indicates it was current at query time.
- The 275-account figure counts only accounts touched by `reference_type = 4`.
  Other kinds of unflagged internal accounts may exist and were not checked.
